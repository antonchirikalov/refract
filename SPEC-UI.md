# SPEC-UI — веб-интерфейс refract (v0.1)

> Дополнение к `SPEC.md` (движок). При расхождении по движку побеждает `SPEC.md`.
> Инварианты движка обязательны и для UI — в первую очередь **I7**: всё
> отображаемое выводится из `state.json` + `events.jsonl`, отдельного состояния
> исполнения у UI нет. **I8**: значения ключей в UI не попадают никогда (только
> имя env-переменной и флаг доступности).

## 1. Что это

Локальное приложение в духе «проект + библиотека шаблонов»: пользователь создаёт
проект, выбирает шаблон пайплайна (или собирает свой), указывает папку с
документами, запускает и смотрит живой прогресс. Аналитик, а не инженер — он не
пишет YAML руками.

Технически: React SPA (Vite + TS) в `web/` поверх REST/WS API §15 движка. Свои
сущности UI не хранит — единственный источник правды остаётся файловым.

**Объём v0.1 (решено 2026-07-25).** Шаблоны пайплайнов пишутся руками (YAML), UI их
только показывает и запускает; редактора пайплайна нет. Отсюда: граф — визуализация,
`PUT` пайплайна из UI не используется (остаётся для CLI и будущего редактора).

**Запуск.** `refract serve` поднимает API на `127.0.0.1:8765` и, если есть
`web/dist`, раздаёт собранный UI там же. Разработка фронта: `npm run dev` в `web/`
(проксирует `/api` на тот же порт).

## 2. Хранение (решено 2026-07-25)

**SQLite не используется.** Причина — I7: БД стала бы вторым источником правды,
который обязан совпадать с файлами. Запуск через CLI, правка YAML в редакторе или
падение между записью файла и записью в БД дают рассинхрон. Папка-проект дружит с
git и бэкапом, БД — нет.

```
~/refract/projects/<project>/        # workspace: один каталог на все проекты
    project.yaml                     # §7; input: — ЛЮБОЙ путь, в т.ч. внешняя папка
    pipelines/<name>.yaml
    runs/<run_id>/…                  # state.json + events.jsonl — источник правды
~/.refract/templates/<name>.yaml     # шаблоны пользователя («сохранить как шаблон»)
~/.refract/providers.yaml  mcp.yaml  # §7, секреты — только имена env-переменных
<library>/templates/<name>.yaml      # шаблоны, поставляемые с движком
```

Список проектов — скан workspace. Список прогонов — скан `runs/`. Папка с
документами живёт ВНЕ проекта и не копируется: `project.yaml: input: <path>`.

**Когда понадобится БД.** Единственный кандидат — кросс-проектный список прогонов
на тысячах записей (сейчас это чтение N маленьких `state.json`, миллисекунды). Тогда
SQLite добавляется как **кэш**, ключ «путь + mtime», с командой пересборки; кэш можно
удалить без потерь. Источником правды он не становится никогда.

## 3. Сущности UI

- **Проект** — папка в workspace. Поля карточки: имя, папка документов, шаблон
  происхождения, дата, последний прогон и его статус.
- **Шаблон** — `pipeline.yaml` + производные метаданные (§5): заголовок, описание,
  из каких узлов состоит, каких агентов и capabilities требует. Два источника:
  поставляемые (read-only) и пользовательские (`~/.refract/templates/`).
- **Пайплайн** — файл проекта. Правится целиком: перезапись + верификация (§19.2
  движка), патч-операций нет.
- **Прогон** — каталог; статусы и события только из леджера (I7).

## 4. Экраны

1. **Проекты** — сетка карточек + «Новый проект».
2. **Новый проект** — имя, выбор шаблона из галереи (или «пустой»), выбор папки
   документов (`GET /api/fs/browse`), модель по умолчанию (`GET /api/models`,
   недоступные провайдеры показаны неактивными). Создание — один POST.
3. **Проект** — граф пайплайна, состояние входа (документы или бриф), список
   прогонов, кнопка «Запустить» (заблокирована, если валидация даёт блокирующие
   ошибки или вход пуст).
4. **Прогон** — граф с подсветкой статусов узлов, живая лента событий (WS
   `?from_seq=`), таймлайн шагов, артефакты по шагам, ответ человеку на
   `waiting_human` (HITL/подтверждения, §16.9/§16.10).
5. **Библиотека шаблонов** — галерея с метаданными, «создать проект из шаблона»,
   «сохранить пайплайн проекта как шаблон».

Граф — read-only визуализация + панель свойств узла. Форма графа приходит с сервера
(`GET .../graph`, §5): узлы, рёбра и топопорядок выводит загрузчик движка, поэтому
клиент не парсит YAML и не может разойтись с валидатором.

**Отрисовка графа.** Слои по зависимостям, рёбра — SVG со стрелками и подписью порта;
ребро, перескакивающее слои, огибает узлы между ними (иначе читается как связь,
которой нет). На узле: вид (`agent`/`loop`/`select`/`discover`/builtin), агент,
бейдж(и) эффективной модели, чип fan-out (`map`/`map_over`), чип `review` у чекпойнта,
статус из леджера. Условные переходы, когда появятся, потребуют только стиля линии и
подписи — раскладка к их смыслу безразлична.

**Логотипы провайдеров.** В комплекте их нет и имитаций не рисуем: это торговые марки.
Файл `web/public/logos/<provider>.svg` (имя = префикс модели до `/`) подхватывается
автоматически; без него — монограмма в цвете провайдера.

## 5. Чего не хватает в API (дельта к §15)

| Нужно | Сейчас | Что добавить |
|---|---|---|
| Создать проект из шаблона с внешней папкой документов | `POST /api/projects {name}` — всегда пустой, всегда `input: ./input` | `{name, template?, input?, model?}` |
| Галерея шаблонов с описанием | только имена (`catalog.templates`) | `GET /api/templates` → метаданные §5.1 |
| Свои шаблоны | нет | `POST /api/templates {name, from_project, pipeline}` → `~/.refract/templates/`; резолвинг шаблонов ищет в обоих каталогах |
| Список прогонов проекта | только по одному run_id | `GET /api/projects/{id}/runs` |
| Документы В проект (новая папка) | `input:` только ссылкой | `POST /api/projects/{id}/input/documents {path, replace}` — копирует; `GET .../input` — что лежит на входе |
| Запрос вместо документов (ресерч) | нет | `PUT /api/projects/{id}/input/brief {text}` → `input/brief.md`, дальше `builtin/brief` + `discover` (SPEC §20) |
| Форма графа для отрисовки | только текст YAML | `GET /api/projects/{id}/pipelines/{name}/graph` |
| Модели для выбора | провайдеры без id моделей | `GET /api/models` отдаёт `models: [...]` — UI строит `provider/model-id` |

### 5.1. Метаданные шаблона

Выводятся из самого файла — отдельного формата не вводим:

```json
{"name": "discovery", "source": "library" | "user",
 "title": "discovery", "description": "<ведущий блок # комментариев файла>",
 "nodes": [{"id": "scan", "type": "builtin/scanner"}],
 "agents": ["source_processor@1", "…"], "needs": ["read", "mcp:tavily-remote"],
 "reads_input_folder": true}
```

`description` — комментарии в шапке файла (всё до ключа `nodes:`; в
`discovery.yaml` описание стоит после `version`/`name`, поэтому «первая строка» не
подходит).
`needs` — объединение capabilities задействованных агентов: UI показывает, что
шаблон полезет в сеть или в bash, ДО запуска. `reads_input_folder` — есть ли
`builtin/scanner`, т.е. обязательно ли указывать папку документов.

## 6. Обязательные тесты

- `test_api_projects_create`: создание из шаблона; `input` наружу проекта попадает в
  `project.yaml` как есть; неизвестный шаблон → 400; дубль имени → 409; путь-обход
  (`..`, абсолютный) в имени → 400.
- `test_api_templates`: перечисление обоих источников; метаданные (агенты, needs,
  `reads_input_folder`, описание из комментария); сохранение своего шаблона; имя,
  конфликтующее с поставляемым → 409.
- `test_api_project_runs`: список прогонов проекта со статусами из `state.json`.
- `test_api_input`: копирование документов (внешняя папка → `input/`), `replace`,
  бриф пишется в `input/brief.md`, пустой бриф → 400.
- `test_api_graph`: узлы/рёбра/порядок совпадают с загрузчиком; неизвестный пайплайн → 404.
- Фронт: e2e не в объёме v0.1; API-контракты покрыты тестами движка, а собранный UI
  проверяется живым смоуком `refract serve` (раздача `index.html` + прогон сценария
  «создать проект из шаблона → задать бриф → граф → валидация»).
