# SPEC-DSL — язык `pipeline.yaml`

Формальное определение языка пайплайна: полный синтаксис, все поля с дефолтами, грамматика
ссылок, система типов артефактов и **все** правила валидации с кодами.

**Отношение к SPEC.md.** SPEC.md остаётся единственным источником истины по семантике
движка (исполнение, леджер, гейты, рантайм). Этот документ — источник истины по **языку**:
что синтаксически допустимо, что валидатор обязан отвергнуть и с каким кодом. При
расхождении этого документа с кодом — это баг, который правится явно в одном из двух мест
(как и с SPEC.md), никогда молча. Разделы SPEC.md, которые здесь конкретизируются: §5
(типы), §6 (пакет агента), §8 (pipeline.yaml), §13 (builtin), §16 (ограничения v0.1),
§20 (discover), §21 (чекпойнты).

Версия языка: `version: "0.1"`.

---

## 1. Модель данных: ноды, порты, артефакты

Пайплайн — это **направленный ациклический граф нод**. Нода — единица планирования и
переиспользования; она может разворачиваться в несколько **шагов** (map по элементам
коллекции, раунды петли), но в графе остаётся одной вершиной.

Каждая нода объявляет **выходные порты** (что она производит) и **входные порты** (что ей
нужно). Порт — именованный артефакт известного типа. Ребро графа — это связь
`вход_ноды_B ← выход_ноды_A`, выраженная строкой-ссылкой в `inputs`.

Ключевое свойство, вытекающее из грамматики: **ссылка адресует ноду по её `id`, а не
«предыдущую» ноду.** Ссылаться можно на любую ноду пайплайна на любом расстоянии вверх по
графу; порядок исполнения выводится из совокупности ссылок (топологическая сортировка,
§7), а не из порядка перечисления нод в файле. Несколько нужных артефактов — это просто
несколько записей в `inputs`; ограничения на их количество нет, ограничение одно: каждый
ключ должен быть портом `consumes` соответствующего агента.

```yaml
# критик дизайна получает черновик из тела своей же петли И документ требований,
# который произвела нода тремя слоями выше
critic:
  agent: solution_design_critic@1
  inputs:
    draft: "@body"
    requirements: refine.doc
```

## 2. Верхний уровень файла

```yaml
version: "0.1"          # обязательно, строка
name: requirements_to_design   # обязательно, строка
input_mode: documents   # documents | brief; по умолчанию documents
checkpoints: [refine]   # список id нод; по умолчанию пусто
nodes: [ ... ]          # обязательно, непустой список нод
```

| Поле | Тип | Дефолт | Смысл |
|---|---|---|---|
| `version` | строка | — | версия формата; сейчас `"0.1"` |
| `name` | строка | — | имя пайплайна (используется в леджере и UI) |
| `input_mode` | `documents` \| `brief` | `documents` | что пайплайн ожидает во входной папке проекта: набор документов для сканера либо один написанный бриф/тему. На исполнение не влияет (и то и другое — файлы в `input/`); это подсказка клиенту, что просить у пользователя (SPEC §8, SPEC-UI §5) |
| `checkpoints` | список id нод | `[]` | ноды, ПОСЛЕ которых ран парковается на выверку человеком (SPEC §21). Уровень пайплайна, а не параметр ноды: применимо к ноде любого вида, а модели параметров у них разные |
| `nodes` | список нод | — | ноды графа; порядок в файле произволен |

Верхний уровень закрыт: неизвестное поле → `E_SCHEMA` (`extra="forbid"` во всех моделях
языка, включая параметры). Это осознанно: опечатка в имени параметра должна ломать
валидацию, а не тихо игнорироваться.

Ссылка в `checkpoints` на несуществующую ноду → `E_UNKNOWN_NODE_REF`.

## 3. Общее для всех нод

```yaml
- id: refine        # обязательно; ^[a-z_][a-z0-9_]*$
  type: loop        # обязательно; дискриминатор вида ноды
```

`id` уникален в пайплайне (иначе `E_DUP_NODE_ID`) и служит адресом в ссылках. Формат id
нарушен → `E_SCHEMA`.

`type` выбирает вид ноды и, соответственно, набор допустимых полей:

| `type` | Вид | Раздел |
|---|---|---|
| `builtin/<name>` | детерминированная нода движка | §4 |
| `agent` | один агент, опционально с fan-out | §5 |
| `loop` | контейнер: тело + критик, раунды по вердикту | §6.1 |
| `select` | контейнер: селектор выбирает победителя из коллекции | §6.2 |
| `discover` | сетевой источник коллекции | §6.3 |

Неизвестный `type` (не из списка и не `builtin/…`) → `E_SCHEMA`.

### 3.1. Параметры и их наследование

`params` есть у всех видов нод. Общая часть (SPEC §8.2):

| Параметр | Тип | Дефолт | Смысл |
|---|---|---|---|
| `gate_retries` | int | `2` | повторов шага после провала гейта; независим от `infra_retries` |
| `infra_retries` | int | `2` | повторов при инфраструктурном сбое |
| `timeout_s` | int \| null | `null` | `null` → берётся из `defaults.timeout_s` агента (иначе 3600) |

Специфичные параметры по видам нод — в соответствующих разделах. Дополнительно у
`agent`/`loop`/`select`/`discover` есть:

| Параметр | Тип | Дефолт | Смысл |
|---|---|---|---|
| `model` | строка \| null | `null` | `provider/model_id`, либо привязка `@<selectId>.winner_model`. `null` → дефолт проекта |
| `cache` | bool | `false` | в v0.1 не поддержан: `true` даёт предупреждение `W_CACHE_UNSUPPORTED` |

Подблоки контейнеров (`body`, `critic`, `selector`) могут переопределить только
`gate_retries`, `infra_retries`, `timeout_s`, `cache` — прочее наследуется от ноды.

## 4. `builtin/<name>` — детерминированные ноды

```yaml
- id: scan
  type: builtin/scanner
  params: { exclude: [drafts], input: ./docs }
```

Нода без LLM: параметры проверяются моделью самого builtin, порты фиксированы (SPEC §13).
Неизвестное имя → `E_SCHEMA`; неверные параметры → `E_SCHEMA` с текстом от модели.

| builtin | Параметры | Производит |
|---|---|---|
| `scanner` | `exclude: list[str]` (точные имена верхнего уровня, дефолт `[]`), `input: str \| null` (переопределение пути) | `sources: collection<source@v1>` |
| `brief` | `file: str` (имя внутри входной папки, дефолт `brief.md`), `input: str \| null` | `brief: brief@v1` |

Builtin-ноды не имеют `inputs`: их вход — входная папка проекта.

## 5. `agent` — один агент

```yaml
- id: extract
  type: agent
  agent: source_processor@1     # name@version из библиотеки
  map: scan.sources             # ЛИБО map, ЛИБО map_over, ЛИБО ничего
  inputs: { requirements: refine.doc }
  params: { workers: 3, min_ok: 1, on_item_failure: skip }
```

| Поле | Тип | Дефолт | Смысл |
|---|---|---|---|
| `agent` | `name@version` | — | ссылка в библиотеку агентов; нет такого → `E_UNKNOWN_AGENT` |
| `inputs` | map `порт → ссылка` | `{}` | ключ обязан быть портом `consumes` агента, иначе `E_UNKNOWN_PORT` |
| `map` | ссылка на коллекцию | `null` | fan-out по элементам коллекции |
| `map_over` | `{models: [...]}` | `null` | fan-out по моделям: один и тот же вход, N моделей |
| `params.workers` | int | `3` | параллелизм fan-out; осмыслен только с `map`/`map_over` |
| `params.on_item_failure` | `skip` \| `fail` | `skip` | судьба ноды при падении элемента |
| `params.min_ok` | int | `1` | сколько элементов должно получиться, иначе нода `failed` |

Выходные порты ноды:

- без fan-out — порты `produces` агента как есть;
- с `map` или `map_over` — **один** порт: `collection<тип первичного порта>`. Первичный
  порт — единственный необязательный (`optional: false`) `produces`; если их не ровно
  один, тип вывода не определён и ссылки на него дадут `E_UNKNOWN_PORT`.

Правила fan-out:

- `map` и `map_over` одновременно → `E_MAP_CONFLICT`;
- источник `map` — не коллекция → `E_TYPE_MISMATCH`;
- источник `map` произведён нодой, которая сама была `map`/`map_over` → `E_NESTED_MAP`
  (вложенный fan-out в v0.1 запрещён, SPEC §16.4);
- элемент коллекции привязывается к **единственному** порту `consumes` с типом элемента;
  если таких портов не ровно один → `E_MAP_PORT_AMBIGUOUS`. Этот порт не нужно (и нельзя
  осмысленно) указывать в `inputs` — он занят элементом;
- `map_over` не потребляет коллекцию: все входы приходят из `inputs`.

## 6. Контейнеры

Контейнер — нода, внутри которой несколько поименованных **элементов** (подблоков), каждый
со своим агентом и моделью. В графе это одна вершина; внутренняя структура видна в
ссылках (`@body`, `@prev`) и в UI (SPEC-UI §2.1).

**Что делает контейнер контейнером.** Не рамка в UI и не «несколько нод внутри», а
контрольное решение, которое движок принимает по **типизированному артефакту** (I4).
Отсюда модель расширения: контейнер = **элементы + ОДИН контроллер + один контрольный
тип**.

| Архетип | Контроллер | Контрольный тип | Решение движка |
|---|---|---|---|
| `loop` | `critic` | `verdict@v1` | повторить тело или выйти |
| `select` | `selector` | `selection@v1` | какой кандидат победил |

Множество архетипов **закрыто**: новый вид контроля добавляется новым архетипом со своим
контрольным типом, а не свободной композицией элементов. Свободный контейнер с условием
выхода, записанным в YAML, рассмотрен и отклонён: условие пришлось бы выражать языком
выражений над артефактами, что ослабляет статическую валидацию и открывает обход I4 (рано
или поздно условие напишут по свободному тексту). По той же причине **критерии выбора** в
`select` живут в промпте агента-селектора (I5), а не в pipeline.yaml: это суждение, а не
механика; YAML лишь указывает, какой селектор взять.

Число элементов, наоборот, не является частью контроля — поэтому цепочка в `body`
разрешена (§6.1).

### 6.1. `loop` — тело + критик

```yaml
- id: refine
  type: loop
  params: { max_rounds: 3, on_max_rounds: pass }
  body:
    agent: requirements_writer@1
    inputs: { extracts: extract.extract }
  critic:
    agent: requirements_critic@1
    inputs: { draft: "@body", extracts: extract.extract }
  outputs: { doc: "@body" }
```

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `body` | блок `{agent, model?, inputs?, params?}` ЛИБО список таких блоков | да | что производит документ; список = цепочка (см. ниже) |
| `critic` | тот же блок | да | судит результат; первичный выход обязан быть `verdict@v1`, иначе `E_LOOP_SHAPE` |
| `outputs` | map `внешний_порт → @body[.порт]` | да | что петля показывает наружу |
| `params.max_rounds` | int (дефолт `3`) | — | максимум раундов |
| `params.on_max_rounds` | `pass` \| `fail` (дефолт `pass`) | — | что делать, если критик так и не одобрил |

`outputs` определяет внешние порты ноды: `@body` — первичный выход тела, `@body.<порт>` —
конкретный порт тела. Ссылки на другие ноды в `outputs` не предусмотрены.

**Цепочка в `body`.** Если `body` — список, его элементы исполняются по порядку внутри
раунда, и каждый может получить выход предыдущего по ссылке `@prev` (или `@prev.<порт>`).
Выход **последнего** элемента и есть черновик раунда: его судит критик (`@body`), из него
собираются `outputs`, из него берётся `_previous` для следующего раунда. Контекст ревизии
(`_previous` + вердикт) отдаётся ТОЛЬКО первому элементу — он переписывает, остальные
обрабатывают полученное.

```yaml
- id: refine
  type: loop
  body:
    - agent: requirements_writer@1        # body1 — пишет
      inputs: { extracts: extract.extract }
    - agent: fact_checker@1               # body2 — сверяет с источниками
      inputs: { draft: "@prev", extracts: extract.extract }
  critic:                                 # контроллер один
    agent: requirements_critic@1
    inputs: { draft: "@body", extracts: extract.extract }
  outputs: { doc: "@body" }
```

Имена элементов для леджера, шагов и адресации в API: цепочка из одного элемента сохраняет
историческое `body`, цепочка длиннее — `body1`, `body2`, …. Правила:

- `@prev` в первом элементе → `E_LOOP_SHAPE` (нет предыдущего);
- `@body` в элементе тела → `E_LOOP_SHAPE` (это выход самого тела, а не соседа);
- `@body`/`@prev` в ноде вне петли → `E_LOOP_SHAPE` (раньше такая ссылка молча
  игнорировалась, и агент работал без артефакта, который автор считал подключённым);
- модель разрешается ДЛЯ КАЖДОГО элемента отдельно (ключ override — `<nodeId>.body2`).

Внутри `body.inputs`/`critic.inputs` допустимы **и** внутренние ссылки (`@body`), **и**
обычные ссылки на любые ноды пайплайна — именно так критик получает материал, против
которого судит (`extracts: extract.extract`). Внутренние ссылки разрешает движок в момент
исполнения, поэтому валидатор их типы не сверяет; внешние — сверяет как обычные рёбра.

Раунды не хранятся в языке: номер раунда выводится из леджера (SPEC §10.3).

### 6.2. `select` — выбор победителя

```yaml
- id: choose
  type: select
  candidates: design.design_doc      # обязана быть коллекция
  selector: { agent: solution_design_selector@1 }
  params: { fallback: first_ok }
```

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `candidates` | ссылка на коллекцию | да | не коллекция → `E_TYPE_MISMATCH` |
| `selector` | блок `{agent, model?, params?}` | да | первичный выход обязан быть `selection@v1`, иначе `E_TYPE_MISMATCH` |
| `params.fallback` | `first_ok` \| `fail` (дефолт `first_ok`) | — | поведение при негодном выборе |

Выходной порт ноды — `out` с типом **элемента** коллекции кандидатов. Кандидаты
привязываются к единственному порту `consumes` селектора, имеющему тип коллекции;
`selector` не имеет `inputs`.

Кроме данных, `select` порождает скалярную привязку `winner_model` — см. §8.2.

### 6.3. `discover` — сетевой источник коллекции

```yaml
- id: find
  type: discover
  agent: source_finder@1
  inputs: { brief: brief.brief }
  params: { min_sources: 3 }
```

| Поле | Тип | Дефолт | Смысл |
|---|---|---|---|
| `agent` | `name@version` | — | агент, ищущий источники в сети |
| `inputs` | map `порт → ссылка` | `{}` | как у обычного агента |
| `params.min_sources` | int | `1` | меньше найдено → нода `failed` |

Выходной порт **фиксирован**: `sources` типа `collection<source@v1>` — независимо от того,
как называется порт самого агента. Агент производит ОДИН каталог, коллекцию собирает
движок (I6): агенты не производят коллекции. Отсюда требования к контракту агента:

- ровно один первичный (`optional: false`) порт `produces`, иначе `E_DISCOVER_SHAPE`;
- его тип — артефакт вида `kind: dir`, иначе `E_DISCOVER_SHAPE`.

## 7. Грамматика ссылок

Три и только три формы (SPEC §8.1):

| Форма | Значение | Где допустима |
|---|---|---|
| `<nodeId>.<port>` | ребро данных: выходной порт **любой** ноды графа | `inputs`, `map`, `candidates` |
| `@body` / `@body.<port>` | выход тела петли (последнего элемента цепочки) | `inputs` критика, `outputs` петли |
| `@prev` / `@prev.<port>` | выход предыдущего элемента цепочки `body` | `inputs` элемента тела, кроме первого |
| `@<selectId>.winner_model` | скалярная привязка модели-победителя | поле `model` ноды/подблока |

Строка, не подходящая ни под одну форму, ссылкой не считается: в `inputs` она не создаёт
ребра (и не проверяется), в поле `model` — трактуется как имя модели `provider/model_id`.
Строка, начинающаяся с `@`, но не совпадающая с формой привязки, в поле `model` даёт
`E_BINDING_ILLEGAL`.

Проверки ссылок данных:

- нода с таким `id` отсутствует → `E_UNKNOWN_NODE_REF`;
- у ноды нет такого выходного порта → `E_UNKNOWN_PORT`;
- дальность не ограничена: ссылка на ноду через любое число слоёв законна и создаёт
  обычное ребро зависимости.

**Порядок исполнения** — топологическая сортировка по совокупности рёбер данных и
скалярных привязок. Контейнер (`loop`) — атомарная вершина: цикл внутри петли не является
циклом графа. Цикл между нодами → `E_CYCLE`.

## 8. Модели и провайдеры

### 8.1. Разрешение модели

Для каждой позиции, требующей модель (нода `agent`/`discover`, подблоки `body`, `critic`,
`selector`), модель берётся в порядке:

1. override рана (ключ `<nodeId>` или `<nodeId>.<block>`);
2. `model` в самой ноде/подблоке;
3. дефолт проекта (`defaults.model`).

Ничего не нашлось → `E_MODEL_UNRESOLVED`. Провайдер (часть до `/`) не сконфигурирован или
его ключ пуст в окружении → `E_PROVIDER_UNAVAILABLE`.

### 8.2. Привязка `winner_model`

`model: "@choose.winner_model"` означает «та модель, чей кандидат победил». Законна только
если:

- `choose` — нода `select` (иначе `E_BINDING_ILLEGAL`);
- её `candidates` происходят от ноды `agent` с `map_over.models` (иначе
  `E_BINDING_ILLEGAL`) — только тогда «модель кандидата» вообще определена.

Все модели из `map_over.models` этой ноды проверяются на доступность провайдера.

## 9. Типы артефактов

Тип артефакта — имя вида `^[a-z][a-z0-9_]*@v\d+$` плюс конструктор коллекции
`collection<X>`. Определения библиотечных типов лежат в
`library/types/artifact_types.yaml`; контрольные типы движок добавляет сам.

| Поле определения | Значения | Смысл |
|---|---|---|
| `kind` | `file` \| `dir` \| `any` | форма артефакта |
| `format` | `json` \| `markdown` \| `text` | расширение файла и способ проверки |
| `schema` | имя файла JSON-схемы | проверка структуры для `format: json` |
| `rules` | список правил | механические проверки содержимого |
| `inline` | bool | можно ли встраивать содержимое в промпт (до 4096 байт) |

Правила (`rules`) — механическая часть контракта, её проверяет **гейт**, а не LLM:

| Правило | Поля | Смысл |
|---|---|---|
| `regex` | `pattern`, `flags?` (`m`,`i`,`s`,`x`,`a`,`u`) | `re.search` по тексту артефакта |
| `min_length` | `value` | минимальная длина в символах |

Контрольные типы (инъектируются движком, ими же принимаются управляющие решения — I4):
`verdict@v1`, `selection@v1`, `question@v1`, `answer@v1`.

Библиотечные типы v0.1: `source@v1`, `extract@v1`, `requirements@v1`, `design_doc@v1`,
`brief@v1`, `found_sources@v1`, `discovery_report@v1`, `arch_report@v1`,
`illustration@v1`, `publication@v1`.

Тип, на который ссылается порт агента, но которого нет в реестре → `E_UNKNOWN_TYPE`.
Попытка переопределить контрольный тип в файле реестра → `E_RESERVED_TYPE`.

### 9.1. Совместимость рёбер

| Источник | Приёмник | Результат |
|---|---|---|
| `T` | `T` | ок |
| `T` | `U` (`T≠U`) | `E_TYPE_MISMATCH` |
| `collection<X>` | `collection<X>` | ок |
| `collection<X>` | `collection<Y>` (`X≠Y`) | `E_TYPE_MISMATCH` |
| `collection<X>` | `X` | ок **только** через `map:` |
| `T` (не коллекция) | `collection<...>` | `E_TYPE_MISMATCH` |

Последняя строка — прямое следствие I6: агент не может произвести коллекцию, её собирает
движок (`map`, `map_over`, `discover`).

## 10. Ограничения контракта агента, проверяемые в графе

Эти правила про `agent.yaml`, но нарушение обнаруживается при валидации пайплайна — с
`node_id` той ноды, которая агента использует:

| Правило | Код |
|---|---|
| ни один `produces` не является коллекцией (I6) | `E_AGENT_PRODUCES_COLLECTION` |
| не больше одного необязательного (`optional`) порта `produces` | `E_MCP_UNDECLARED` | агент требует `mcp:<server>`, которого нет в конфиге MCP (проверка пропускается, если конфиг не загружен) |
| `E_HITL_SHAPE` |
| необязательный порт имеет тип `question@v1` | `E_MCP_UNDECLARED` | агент требует `mcp:<server>`, которого нет в конфиге MCP (проверка пропускается, если конфиг не загружен) |
| `E_HITL_SHAPE` |
| каждый обязательный порт `consumes` подключён (`inputs`, либо элемент `map`) | `E_INPUT_MISSING` |
| каждый MCP-сервер из `needs: [mcp:<server>]` объявлен в конфиге MCP | `E_MCP_UNDECLARED` |

`E_MCP_UNDECLARED` не выдаётся, если конфиг MCP вообще не загружен (контекст без
конфигурации) — тогда проверка пропускается; CLI и API всегда передают реальный набор.

## 11. Порядок фаз валидации

Валидатор **собирает** все находки как структурные записи `{code, node_id, message}` и
никогда не бросает их по одной. Порядок фаз (SPEC §8.3):

1. YAML → `E_YAML`; схема pydantic → `E_SCHEMA`;
2. уникальность id → `E_DUP_NODE_ID`;
3. существование builtin/агентов/типов + проверка MCP → `E_SCHEMA`, `E_UNKNOWN_AGENT`, `E_UNKNOWN_TYPE`, `E_MCP_UNDECLARED`;
4. существование ссылок (ноды и порты) → `E_UNKNOWN_NODE_REF`, `E_UNKNOWN_PORT`; ссылки в `checkpoints`;
5. **если** предыдущие фазы не дали блокирующих находок — форма нод (`map`, петля, select, discover) и совместимость рёбер + полнота входов;
6. ацикличность → `E_CYCLE`;
7. разрешимость моделей и провайдеров → `E_MODEL_UNRESOLVED`, `E_PROVIDER_UNAVAILABLE`, `E_BINDING_ILLEGAL`;
8. предупреждения → `W_CACHE_UNSUPPORTED`, `W_SECURITY`.

Фаза 5 пропускается при неразрешённых ссылках намеренно: проверять типы рёбер, когда
неизвестно, что за нода на другом конце, — значит выдавать каскад ложных ошибок поверх
одной настоящей.

Пайплайн валиден, если нет находок с кодом `E_*`; `W_*` не блокируют.

## 12. Полный перечень кодов

| Код | Когда |
|---|---|
| `E_YAML` | файл не парсится как YAML |
| `E_SCHEMA` | нарушена схема языка: неизвестное поле, неверный `id`/`type`, неизвестный builtin, негодные параметры builtin |
| `E_DUP_NODE_ID` | два узла с одним `id` |
| `E_UNKNOWN_NODE_REF` | ссылка (или чекпойнт) на несуществующую ноду |
| `E_UNKNOWN_PORT` | нет такого выходного порта у источника, либо ключ `inputs` не является портом `consumes` |
| `E_UNKNOWN_AGENT` | нет такого `name@version` в библиотеке |
| `E_UNKNOWN_TYPE` | порт агента ссылается на незарегистрированный тип |
| `E_RESERVED_TYPE` | попытка переопределить контрольный тип |
| `E_TYPE_MISMATCH` | несовместимое ребро; `map`-источник не коллекция; `candidates` не коллекция; первичный выход селектора не `selection@v1` |
| `E_INPUT_MISSING` | обязательный порт `consumes` не подключён |
| `E_CYCLE` | цикл в графе нод |
| `E_MODEL_UNRESOLVED` | модель не выводится ни из ноды, ни из override, ни из дефолта проекта |
| `E_PROVIDER_UNAVAILABLE` | провайдер не сконфигурирован либо его ключ пуст |
| `E_MAP_CONFLICT` | одновременно `map` и `map_over` |
| `E_MAP_PORT_AMBIGUOUS` | не ровно один порт `consumes` с типом элемента коллекции |
| `E_NESTED_MAP` | источник `map` произведён `map`/`map_over`-нодой |
| `E_LOOP_SHAPE` | первичный выход критика петли не `verdict@v1`; `@prev` в первом элементе цепочки; `@body` в элементе тела; `@body`/`@prev` вне петли |
| `E_BINDING_ILLEGAL` | негодная привязка `winner_model` (не `select`; кандидаты не из `map_over`; неразбираемая `@`-строка в `model`) |
| `E_AGENT_PRODUCES_COLLECTION` | агент объявил `produces` с типом коллекции (I6) |
| `E_MCP_UNDECLARED` | агент требует `mcp:<server>`, которого нет в конфиге MCP (проверка пропускается, если конфиг не загружен) |
| `E_HITL_SHAPE` | больше одного необязательного `produces`, либо его тип не `question@v1` |
| `E_DISCOVER_SHAPE` | агент `discover`-ноды не имеет ровно одного первичного порта вида `dir` |
| `W_CACHE_UNSUPPORTED` | `cache: true` (в v0.1 не реализовано) |
| `W_SECURITY` | нода, достижимая от сканера, использует `bash`/`webfetch`/`mcp:*` — путь «недоверенный документ → инструмент» |

Перечень **закрыт**: новый код добавляется правкой этого документа и SPEC §8.3 в том же
коммите. Тест `tests/test_dsl_spec.py` следит, чтобы перечень здесь и `Code` в коде не
разъезжались.

## 13. Пример: все конструкции языка в одном файле

```yaml
version: "0.1"
name: full
input_mode: documents
checkpoints: [refine]

nodes:
  - id: scan
    type: builtin/scanner

  - id: extract                       # fan-out по элементам коллекции
    type: agent
    agent: source_processor@1
    map: scan.sources
    params: { workers: 3, min_ok: 1 }

  - id: refine                        # контейнер: тело + критик
    type: loop
    params: { max_rounds: 3 }
    body:
      agent: requirements_writer@1
      inputs: { extracts: extract.extract }
    critic:
      agent: requirements_critic@1
      inputs: { draft: "@body", extracts: extract.extract }
    outputs: { doc: "@body" }

  - id: design                        # fan-out по моделям
    type: agent
    agent: solution_designer@1
    inputs: { requirements: refine.doc }
    map_over: { models: ["kimi/k3", "openai/gpt-5.6"] }

  - id: choose
    type: select
    candidates: design.design_doc
    selector: { agent: solution_design_selector@1 }

  - id: sd_refine
    type: loop
    params: { model: "@choose.winner_model" }   # скалярная привязка
    body:
      agent: solution_designer@1
      inputs: { requirements: refine.doc }      # ссылка через три слоя вверх
    critic:
      agent: solution_design_critic@1
      inputs: { draft: "@body", requirements: refine.doc }
    outputs: { design: "@body" }
```
