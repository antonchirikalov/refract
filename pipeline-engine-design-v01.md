# Дизайн движка пайплайнов: проработка открытых зон (pre-spec, v0.1)

Документ закрывает пять зон, не покрытых базовой моделью (типы артефактов, порты, map/collection, пакеты агентов, AgentRuntime-адаптер), плюс «второй ряд» вопросов. Формат: для каждой зоны — принятое решение, семантика, что запрещено в v0.1.

Принятые ранее решения (контекст): декларативный граф `pipeline.yaml` + универсальный исполнитель; реестр именованных типов артефактов (`extract@v1`, …); агенты «один вход → один выход», множественность только через map-ноды и `collection<X>`; агент — пакет (`agent.yaml` + `prompt.md` + схемы), компилируемый адаптером в формат раннера (opencode serve — первая реализация); проект — самодостаточная папка; агенты не знают путей проекта, движок материализует входы в workdir шага.

---

## 1. Control flow: мета-ноды `loop` и `select`

### 1.1. Принцип

Граф верхнего уровня — строгий DAG. Циклы и ветвление по данным существуют только внутри двух закрытых мета-нод, реализованных движком. Ключевое правило, снимающее проблему «данные становятся управлением»:

> Управляющие решения принимает только движок, и только читая артефакты специальных типов из реестра (`verdict@v1`, `selection@v1`, `question@v1`). Агент никогда не управляет графом — он лишь производит типизированный артефакт, который движок интерпретирует.

Никакого парсинга свободного текста («VERDICT: APPROVED» в markdown) — управляющие артефакты только JSON со схемой. Это переносится из spectra с ужесточением: verdict сейчас парсится из текста, в новой системе критик обязан выдать `verdict.json`.

Управляющие типы в реестре:

```yaml
verdict@v1:    # выход критика
  kind: file
  format: json
  schema:      # { verdict: "approved" | "revise", issues: [{section, note}] }

selection@v1:  # выход селектора
  kind: file
  format: json
  schema:      # { winner: "<slug>", rationale: "..." }

question@v1:   # HITL, см. раздел 3
  kind: file
  format: json
  schema:      # { question, context, options?: [...] }

answer@v1:     # HITL, пишет движок
  kind: file
  format: json
```

### 1.2. Мета-нода `loop` (паттерн writer ↔ critic)

```yaml
- id: refine
  type: loop
  max_rounds: 5
  on_max_rounds: pass          # pass = предупреждение, взять последнюю версию; fail = нода failed
  body:
    agent: requirements_writer
    inputs: { extracts: extract.out }
  critic:
    agent: requirements_critic
    inputs: { doc: "@body", extracts: extract.out }   # @body — выход body текущего раунда
  outputs:
    doc: "@body"               # что нода экспортирует наружу
```

Семантика раунда r:

1. Движок запускает body. Раунд 1 — обычный запуск. Раунд ≥ 2 — тот же агент, но движок добавляет к промпту стандартный revision-хвост: путь к предыдущей версии + содержимое `verdict.json` (инлайном — он маленький). Автор агента revision-промпт руками не пишет; при необходимости в пакете агента есть опциональная секция `revision_hint` в `prompt.md`.
2. Валидационный гейт body (как у любого шага).
3. Движок запускает critic. Гейт: выход обязан пройти схему `verdict@v1`.
4. Движок читает verdict: `approved` → цикл завершён, наружу отдаётся body раунда r; `revise` и r < max_rounds → раунд r+1; `revise` и r == max_rounds → политика `on_max_rounds`.

Инварианты:

- Step ID: `refine.body:r1`, `refine.critic:r1`, `refine.body:r2`, … — прямое продолжение схемы spectra (`critic:r2`, `revision:r1`).
- Каждый раунд — отдельные step-каталоги; артефакты иммутабельны, история раундов сохраняется целиком.
- Счётчик раундов не хранится отдельно — он выводится из леджера (сколько шагов `refine.critic:*` завершено). Resume бесплатен: движок видит последний завершённый шаг и продолжает с него.
- Тип выходного порта `loop` = тип соответствующего порта body. Для типизации рёбер снаружи `loop` выглядит как обычная нода.
- UI: одна нода с бейджем «round 2/5», раскрывается в таймлайн раундов.

Ограничения v0.1: body — ровно один агент, critic — ровно один агент. Не цепочка, не map, не вложенный loop. Если body должен быть цепочкой — это сигнал вынести подготовку данных в отдельные ноды до цикла.

### 1.3. Мета-нода `select` (паттерн «N кандидатов → победитель»)

```yaml
# Кандидаты: map по моделям, а не по коллекции данных
- id: design
  agent: solution_designer
  inputs: { requirements: refine.doc }
  map_over:
    models: [kimi/kimi-k3, openai/gpt-5.6]   # → collection<design-doc@v1>, slug = model slug

- id: choose
  type: select
  candidates: design.out
  selector:
    agent: solution_design_selector
  fallback: first_ok           # селектор упал → первый успешный кандидат
```

Семантика:

- Вход — всегда `collection<X>`. Если в коллекции один успешный элемент — селектор не запускается, элемент проходит насквозь (поведение spectra).
- Селектор обязан выдать `selection@v1`; движок резолвит `winner` по slug в манифесте коллекции и экспортирует артефакт победителя как `choose.out` (тип `X`).
- `map_over.models` — второй легальный вид fan-out наряду с map по коллекции: тот же агент, N моделей, slug элемента = slug модели. Покрывает SD Phase 1 spectra один в один.

Метаданные победителя: `select` экспортирует, кроме `out`, скалярный `winner` (slug). Единственное разрешённое использование — биндинг параметров ниже по графу:

```yaml
- id: sd_refine
  type: loop
  body:
    agent: solution_designer
    model: "@choose.winner"    # ревизию делает победившая модель — паттерн spectra
    inputs: { requirements: refine.doc, draft: choose.out }
  critic: { agent: solution_design_critic, inputs: { doc: "@body" } }
```

Это не язык выражений: движок разрешает ровно один вид ссылки — «скалярный экспорт мета-ноды → параметр ноды». Условия, арифметика, шаблоны — запрещены.

### 1.4. Что запрещено в v0.1

Произвольные условные рёбра; циклы вне `loop`; вложенные `loop`/map внутри map; `select` не от коллекции; динамическое изменение графа из агента. Каждое ослабление — отдельное решение в будущих версиях, не «само получилось».

## 2. Идентичность нод, лок графа, снапшоты

### 2.1. Решение: граф лочится на время рана

- Один активный ран на проект (v0.1). Пока ран в состоянии `running | paused | waiting_human` — `pipeline.yaml` в UI и через чат read-only. Правки — только между ранами.
- Ран при старте делает **снапшот**: в `runs/<run_id>/` копируются `pipeline.yaml`, разрезолвленные параметры (модель на каждой ноде после применения приоритетов), и content-hash каждого пакета агента. Resume работает всегда со снапшотом, никогда с живым файлом. Следствия: правка графа между ранами не может испортить старый ран; любой ран воспроизводим и объясним («этот результат сделан вот этим графом, вот этими промптами, вот этими моделями»).

### 2.2. Стабильные node id

- `id` ноды — обязательный, человекочитаемый, уникальный, неизменяемый ключ. Всё висит на нём: step id, каталоги, статусы в UI, `--force-step`, ссылки `@node.port`.
- LLM-редактирование графа — не перегенерация файла, а **патч-операции**: `add_node`, `remove_node`, `set_param`, `connect`, `disconnect`, `rename_node` (явная, отражается в истории). Билдер-LLM получает текущий YAML и выдаёт список операций; движок применяет их и прогоняет валидатор. Это дешевле для модели, безопаснее для идентичности и даёт готовый undo/redo и человекочитаемый лог изменений в чате («добавил ноду X, соединил с Y»).
- Валидатор после патча дополнительно проверяет: id не переиспользован для ноды с другим агентом (защита от «тихой подмены смысла» при совпадении имени).

## 3. HITL (human-in-the-loop)

### 3.1. Механизм: вопрос — это артефакт, ожидание — это состояние шага

Runtime-agnostic конвенция (никаких специальных тулзов у раннера):

- Агент, которому разрешено спрашивать, декларирует опциональный выходной порт: `produces: [{port: clarification, type: question@v1, optional: true}]`.
- Если после завершения шага в выходе лежит `question.json` (и нет основного артефакта) — движок не считает шаг ни `done`, ни `failed`, а переводит в **`waiting_human`** и пишет это в леджер. Состояние переживает перезапуск приложения — при старте движок видит `waiting_human` и снова показывает вопрос в UI.
- UI: вопрос всплывает в чат-панели (и бейдж на ноде). Ответ пользователя сохраняется движком как `answer@v1` в каталог шага — вопрос и ответ становятся частью артефактной истории рана.
- Движок перезапускает шаг; стандартный хвост промпта включает всю Q&A-историю шага. Лимит — параметр ноды `max_clarifications: 2` (дефолт из spectra); превышение → политика `on_clarification_limit: proceed | fail` (дефолт `proceed`: «отвечай с разумными допущениями, зафиксируй их в assumptions»).

### 3.2. Правила

- Параллельные шаги не блокируются чужим ожиданием: map-нода может иметь 3 done, 1 waiting_human, 2 running.
- Interactive-режим — свойство рана, не графа: `interactive: false` → движок трактует `question.json` по политике `on_clarification_limit` сразу (полностью автономный прогон).
- Пауза по инициативе пользователя — отдельный механизм: graceful stop между шагами (in-flight шаги дорабатывают), состояние `paused`, продолжение = resume. Kill in-flight шага — только через cancel рана.

## 4. Безопасность

### 4.1. Изоляция шага — физическая

- Адаптер раннера обязан ограничить файловый доступ агента каталогом шага. Для opencode: пакет агента компилируется прямо в workdir шага, и `opencode serve` запускается с project root = workdir. Агент физически не видит ни проект, ни другие шаги — не по соглашению, а по конструкции.
- Входы материализуются в `input/` шага (symlink read-only где возможно, иначе copy). Выход — только `output/`.

### 4.2. Тиры capabilities

`needs` агента раскладывается на три тира с разными правилами согласия:

| Тир | Capabilities | Правило |
|---|---|---|
| safe | read, edit, vision | Разрешены всегда, молча |
| network | webfetch, tavily, mcp:* (сетевые) | Согласие на уровне проекта, один раз |
| dangerous | bash, mcp с записью во внешние системы (Jira, Confluence) | Явное подтверждение в UI на конкретную ноду при создании/правке графа; бейдж на ноде |

- Валидатор графа выдаёт **security warnings** по правилу «недоверенный вход + опасная capability»: нода, читающая пользовательские документы (вход от сканера), не должна иметь bash/network. Источник промпт-инъекций — входные PDF/DOCX; агент с bash, читающий их, — готовая дыра. Warning не блокирует, но требует явного «понимаю» в UI.
- Auto-approve permissions раннера (аналог `--dangerously-skip-permissions`) остаётся — но только внутри уже изолированного workdir и уже согласованных тиров. Санбокс уровня контейнера — v0.2+, в v0.1 изоляция файловая + тиры.

### 4.3. Секреты

Ключи провайдеров живут в конфиге приложения (keychain/.env приложения), никогда — в папке проекта (она переносимая и попадает в git). Движок инжектит в окружение шага только ключ провайдера назначенной модели + токены MCP из задекларированных `needs`. Агент с `needs: [read]` не получает в env ни одного лишнего секрета.

## 5. Кэш, resume, повторные запуски

Три разных механизма, которые нельзя смешивать:

1. **Resume** (внутри рана): завершённые шаги рана не перезапускаются никогда; `running` на старте сбрасывается в `pending`; `failed` перезапускается по `--retry-failed`/кнопке. Это spectra as-is, работает по леджеру, хэши не нужны.
2. **Reuse + force** (между ранами): новый ран с параметрами `reuse_from: <run_id>` и `force: [node_id...]`. Движок копирует (линкует) артефакты завершённых шагов старого рана для всех нод выше force-набора, а force-ноды и всё вниз по графу выполняет заново. Покрывает оба главных сценария: «перегенерить с ноды X» (spectra `--force-step`) и «добавил файл в input» (сканер увидит новый элемент, map выполнит только его — элементы map сравниваются по slug и хэшу источника, это единственное место, где в v0.1 нужны хэши).
3. **Content-addressed кэш** (opt-in, фаза 2): `cache: true` на ноде, ключ = hash(пакет агента + параметры + модель + хэши входов). По умолчанию выключен для LLM-нод — недетерминизм и желание пользователя перегенерировать при тех же входах делают молчаливый кэш сюрпризом. Для builtin-нод (сканер, адаптеры) — включён всегда, они детерминированы.

Дефолт UI: кнопка «Rerun from here» на ноде = новый ран с `reuse_from` + `force`. Это главный ежедневный инструмент, и он не требует никакой хэш-магии.

## 6. Второй ряд решений

**Большие коллекции и сборка промпта.** Железное правило стандарта: в промпт попадают только манифесты и пути, никогда содержимое артефактов — агент читает файлы сам. Два исключения: управляющие артефакты (`verdict`, `answer`) инлайнятся (они маленькие по схеме), и артефакт с флагом `inline: true` в реестре типов при размере < 4 КБ. Если манифест коллекции > 50 элементов — движок инжектит сводку (счётчики + первые 50 + «полный список в _collection.json»).

**Троттлинг провайдеров.** Семафоры на уровне движка: `providers.yaml` задаёт `max_concurrent` и `rpm` на провайдера; фактический параллелизм map-ноды = min(workers ноды, свободные слоты провайдера её модели). 429/5xx — забота адаптера: ретраи с backoff, и такие ошибки классифицируются как `failed_infra`, не как ошибка агента (не тратят попытки валидационного гейта).

**Таксономия исходов шага.** `ok | failed_validation | failed_agent | failed_infra | timeout | cancelled | waiting_human`. Ретрай-политики различаются: `failed_infra` — автоматически и бесплатно; `failed_validation` — с инжекцией ошибок гейта в промпт, до N попыток; `failed_agent` — по политике ноды. Элементы map несут исход каждый свой; нода агрегирует по `on_item_failure` и `min_ok`.

**События движок → UI.** Один упорядоченный поток на ран, персистится как `events.jsonl` (расширение `agent.events.jsonl` из spectra): `{seq, ts, step_id, type, payload}`, типы: `step_state_changed | heartbeat | tool_call | question | log | run_state_changed`. UI — чистая проекция потока; реконнект = replay с offset. Никакой второй «правды» для UI не существует.

**Каталог агентов для билдер-LLM.** Билдер получает: карточки всех пакетов агентов (name, description, consumes, produces, needs, тир опасности), реестр типов, описание двух мета-нод, 3–4 few-shot примера графов. Выдаёт патч-операции (раздел 2.2); ошибки валидатора возвращаются дословно, до 3 попыток, дальше — честное «не смог, вот что не сходится» в чат.

**Жизненный цикл рана.** `created → validating → running ⇄ (paused | waiting_human) → completed | failed | cancelled`. Cancel — graceful с грейс-периодом, потом kill in-flight шагов; их step-каталоги помечаются `cancelled`, артефакты не удаляются.

## 7. Явные ограничения v0.1

1. Один активный ран на проект; граф залочен на время рана, правки — только между ранами.
2. Control flow — только мета-ноды `loop` и `select`; никаких условных рёбер и выражений.
3. `loop`: body и critic — по одному агенту; вложенные loop/map запрещены.
4. Fan-out — только map по коллекции или `map_over.models`; вложенный map запрещён; агент не может сам порождать коллекцию.
5. Скалярные биндинги — только «экспорт мета-ноды → параметр ноды».
6. Кэш по контенту — выключен для LLM-нод (opt-in — фаза 2); межранное переиспользование — только через `reuse_from + force`.
7. Изоляция — файловая (workdir + тиры capabilities); контейнерный санбокс — v0.2.
8. Правки графа — патч-операциями со стабильными id; массовая перегенерация YAML запрещена.
9. Управляющие артефакты — только JSON по схеме; парсинг маркеров из свободного текста запрещён.

## 8. Оставшиеся открытые вопросы (осознанно не решены)

- **Версионирование пакетов агентов между проектами**: агенты живут в проекте или в общей библиотеке с версиями? Пока предположение: общая библиотека, проект пинит версии в снапшоте рана. Надо решить до спеки формата пакета.
- **Миграция типов** (`extract@v1 → @v2`): реестр версионирован, но процесс апгрейда живых пайплайнов не описан. Не блокирует v0.1 (все на @v1).
- **Оценка стоимости рана** (токены × модель × параллелизм) до запуска — хочется в UI, требует статистики по агентам. Фаза 2.
- **Мультипроектность движка** (несколько проектов параллельно в одном приложении) — влияет только на семафоры провайдеров, решаемо позже.

Следующий шаг: спека форматов (`artifact_types.yaml`, пакет агента, `pipeline.yaml`, `project.yaml`, события, REST/WS API движка) — все решения для неё теперь есть.
