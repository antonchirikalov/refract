# refract — архитектура

> Технический разбор для инженеров: какие принципы лежат в основе движка, как устроено
> исполнение, состояние и восстановление. Формальный источник правды — внутренняя
> спецификация (SPEC.md, в репозиторий не входит);
> здесь — связное объяснение поверх него, без построчного разбора кода.

![refract — прелом­ление одного запроса в конвейер агентов](architecture/hero-pipeline.png)

---

## 1. Что это и какую задачу решает

refract исполняет декларативные пайплайны из LLM-агентов. Работа описывается как граф в
`pipeline.yaml`; универсальный движок исполняет любой такой граф без кодогенерации. Между
шагами передаются типизированные артефакты — файлы на диске со строгим контрактом. Каждый
запуск (run) изолирован, воспроизводим и резюмируем после сбоя.

Ближайшая аналогия — оркестратор задач (Airflow / CI): DAG из шагов, но шаг — это вызов
LLM-агента, а рёбра графа переносят типизированные файлы, а не просто «успех/провал».
Отличие от «просто скрипта с вызовами LLM» — в том, что весь control flow, изоляция,
ретраи, агрегация и восстановление вынесены в движок и подчинены жёстким инвариантам, а
агент остаётся тупым исполнителем одной задачи.

Референс — реальный проект spectra (пайплайны Extract, Discovery, Solution Design): его
сценарии — приёмочные тесты миграции.

## 2. Принципы дизайна (то, ради чего всё построено)

Прежде чем разбирать модули, полезно понять девять принципов — из них выводится почти всё
остальное. В коде они закреплены как инварианты I1–I10 (SPEC §2); нарушение любого — баг по
определению, даже при зелёных тестах.

1. Логика — в данных, а не в коде. Движок знает только 5 примитивов (см. §4) и умеет их
   комбинировать. Новый workflow = новый YAML + новые пакеты агентов; код движка не меняется.
   Это делает поведение декларативным и проверяемым статически (валидатор графа, §12).

2. Всё общение — через файлы на диске. Нет разделяемого состояния в памяти между шагами,
   нет очередей сообщений. Выход шага — это дерево файлов. Отсюда автоматически следуют
   воспроизводимость, отлаживаемость (можно открыть любой промежуточный артефакт) и
   резюмируемость.

3. Контентная адресация. Элементы идентифицируются по `source_hash` = sha256 их содержимого
   (не по времени модификации). Это фундамент reuse: при повторном запуске движок диффит
   элементы по хэшу и переисполняет только изменившиеся.

4. Типизированные контракты + гейт. Каждый порт агента имеет тип из реестра (§5). После
   исполнения гейт проверяет выход по контракту: файл существует, JSON валиден по схеме,
   правила (regex, min_length) выполнены. Гейт — это система типов, действующая на границе
   «агент → движок»: LLM может ошибиться, поэтому его выход не доверяется, а верифицируется.

5. Управление — только через типизированные управляющие артефакты. Решения «крутить цикл /
   выбрать кандидата / спросить человека» движок принимает, читая `verdict@v1` /
   `selection@v1` / `question@v1`. Парсинг маркеров из свободного текста запрещён. Причина:
   детерминизм и аудит — решение всегда объяснимо конкретным JSON-файлом на диске.

6. Изоляция шага (песочница). Агент видит только свой workdir: входы в `input/<port>/`,
   выход в `output/`. Ни один путь вне workdir в промпт не попадает; всё нужное движок
   материализует в `input/` сам. Это даёт безопасность (агент не гуляет по проекту),
   воспроизводимость и параллелизуемость (шаги независимы).

7. Иммутабельность завершённого + архив попыток. Каталог шага в статусе done/reused не
   мутируется. Любой повторный прогон (гейт-ретрай, force, resume) сначала архивирует
   прежнее состояние в `attempts/<n>/`, затем создаёт `output/` заново. История не теряется.

8. Event sourcing и проекции. Состояние живёт в двух файлах: `state.json` (текущий снимок,
   пишется только движком, только атомарно) и `events.jsonl` (append-only журнал с
   монотонным `seq`). Всё, что видит пользователь (CLI, будущий UI), — проекция этих двух
   файлов; отдельного состояния исполнения нет.

9. Дисциплина фаз. Функциональность будущих фаз не реализуется раньше времени; текущая фаза
   ведётся в [PROGRESS.md](../PROGRESS.md). Это удерживает объём и не даёт коду обогнать спеку.

## 3. Два мира: примитивы и агенты

Частая путаница новичка — смешать «примитивы движка» и «агентов». Это ортогональные слои.

| | Примитивы (формы) | Агенты (начинка) |
|---|---|---|
| Что это | типы нод в графе | пакеты в `library/agents/` |
| Кто знает | движок (захардкожено) | библиотека (данные) |
| Сколько | ровно 5 | сколько угодно |
| Пример | `builtin`, `agent`, `map`, `loop`, `select` | `source_processor`, `requirements_critic` |

Примитив задаёт форму исполнения (как гонять поток). Агент — начинку (что за работа).
В `pipeline.yaml` они собираются вместе: «форма `loop`, в `body` — начинка `writer`, в
`critic` — начинка `critic`».

Ключевой момент: роль агента задаёт не форма, а его `produces` (единственный не-optional
выходной порт):

- выдаёт `verdict@v1` (approved/revise) — критик, ставится в `loop.critic`;
- выдаёт `selection@v1` (winner) — селектор, ставится в `select.selector`;
- выдаёт обычный артефакт (`extract@v1`, `design_doc@v1`) — исполнитель.

Движок не различает агентов «по смыслу» — он лишь проверяет валидатором, что на своё место
в форме поставлена начинка нужного типа (иначе `E_LOOP_SHAPE` / `E_TYPE_MISMATCH`).

Пакет агента (SPEC §6) — это папка: `agent.yaml` (контракт: `consumes`, `produces`, `needs`,
`defaults`), `prompt.md` (системный промпт, чистый текст), опционально `revision_hint.md`.
Инвариант I5: секции промпта про входы/выходы генерируются движком из контракта — автор их
руками не пишет. Инвариант I6: агент никогда не производит коллекцию; размножение — дело map.

## 4. Модель — параметр запуска, а не свойство агента

Пакет агента не привязан к модели. Какая модель исполнит агента — определяется снаружи, с
чётким приоритетом (SPEC §7, сверху вниз побеждает первое сработавшее):

1. оверрайд запуска: `refract run … --model-for extract=openai/gpt-5.6`
   (ключ — `node_id`, либо `node_id.body` / `node_id.critic` / `node_id.selector`);
2. `model:` в самой ноде или суб-блоке пайплайна;
3. `defaults.model` проекта (`project.yaml`).

```yaml
# pipeline.yaml — разные модели на разных нодах и суб-блоках
- id: sd_refine
  type: loop
  body:   { agent: solution_designer@1,       model: "@choose.winner_model" }
  critic: { agent: solution_design_critic@1,  model: kimi/kimi-k3 }
```

Следствия:

- один агент можно гонять на разных моделях в разных нодах;
- в `loop` у `body` и `critic` модели независимы (дорогая пишет — дешёвая критикует, или
  наоборот);
- `map_over: { models: [kimi/kimi-k3, openai/gpt-5.6] }` запускает один агент сразу на
  нескольких моделях (fan-out по моделям), выход — `collection<тип основного порта>`, слаг
  элемента = слаг модели; далее `select` выбирает лучший результат;
- строка модели — `provider/model-id`; провайдер обязан быть в `~/.refract/providers.yaml`
  и «доступен» (env-переменная с ключом непуста), иначе `E_MODEL_UNRESOLVED` /
  `E_PROVIDER_UNAVAILABLE` ещё на валидации;
- особый случай — `model: "@<select>.winner_model"`: модель берётся из результата select
  (существует, только если кандидаты произведены `map_over.models`, иначе `E_BINDING_ILLEGAL`).

## 5. Типы артефактов и совместимость рёбер

Реестр типов (`library/types/artifact_types.yaml`, SPEC §5). Запись типа: `kind`
(file/dir/any), `format` (json/markdown/text — только для file), `schema` (JSON Schema для
json), `rules` (закрытый набор: `regex`, `min_length` — по содержимому file), `inline`
(разрешить инлайнить в промпт при размере < 4 KB).

Встроенные управляющие типы движок инжектит сам и запрещает переопределять (`E_RESERVED_TYPE`):
`verdict@v1`, `selection@v1`, `question@v1`, `answer@v1`. Именно они несут control flow (§2,
принцип 5).

Коллекция — не запись реестра, а конструктор `collection<X>`: каталог с манифестом
`_collection.json`, где перечислены элементы (`slug`, `source`, `source_hash`, `status`,
`path`) и агрегированная статистика. failed-элементы остаются в манифесте (payload может
отсутствовать).

Совместимость рёбер (проверяет валидатор): `T → T` точно по имени с версией; `collection<X>`
соединим с входом `collection<X>` напрямую, либо со входом `X` — но только через `map:`.
Иное — `E_TYPE_MISMATCH`.

## 6. Сквозной поток данных на примере Extract

Пайплайн `scan → map(extract) → loop(refine)` — минимальный реалистичный сценарий.

![Поток данных Extract: input → scan → коллекция → map по элементам → коллекция результатов → loop с критиком → итоговый документ](architecture/pipeline-dataflow.png)

Что происходит по стадиям:

1. `scan` (builtin) читает `input/`, выдаёт `collection<source@v1>` — опись всех источников.
2. `map(extract)` разворачивает агента `source_processor` на каждый ok-элемент коллекции;
   выход — `collection<extract@v1>` (по одному извлечению на источник).
3. `loop(refine)` собирает из извлечений единый документ: `body` (`requirements_writer`)
   пишет черновик, `critic` (`requirements_critic`) выдаёт `verdict@v1`; при `revise` — новый
   раунд, при `approved` (или исчерпании `max_rounds`) — выход = документ последнего раунда.

Физически всё это ложится в каталог рана (SPEC §9):

```
runs/run_20260719_101500/
  snapshot/                 # замороженная копия: pipeline.yaml, resolved.yaml,
                            #   полные пакеты агентов, agents.lock.json (хэши пакетов)
  state.json                # текущий снимок состояния (nodes + steps)
  events.jsonl              # append-only журнал событий
  steps/
    scan/main/output/sources/_collection.json
    extract/rfp-pdf/{input,output,prompt.md,raw.txt,attempts/…}
    extract/_out/extract/_collection.json      # собранная выходная коллекция
    refine/body_r1/…  refine/critic_r1/…  refine/body_r2/…
    refine/_out/doc.md
  .active.lock              # pid активного рана (энфорс «один активный ран на проект»)
```

Здесь видно каждый принцип из §2: файлы на диске, изоляция по workdir шага, снапшот для
воспроизводимости, два уровня состояния.

## 7. Сканер — вход в мир коллекций

![Сканер раскладывает кучу документов по пронумерованным ячейкам и ведёт опись](architecture/scanner.png)

Сканер отвечает на вопрос «что нам дали на вход». Агент работает по принципу «одна задача за
запуск» (I6) и не умеет разгребать папку — сканер превращает произвольный `input/` в
структурированную коллекцию задач ([refract/builtins/scanner.py](../refract/builtins/scanner.py)):

- смотрит верхний уровень `input/` (не рекурсивно); каждый файл и каждая подпапка целиком →
  один элемент `source@v1` (подпапка = один источник);
- присваивает slug (`rfp.pdf` → `rfp-pdf`, коллизии → суффикс `-2`, `-3`; порядок обхода
  отсортирован, поэтому слаги детерминированы);
- считает `source_hash` = sha256 содержимого (для папки — sha256 отсортированных пар
  `relpath:sha256(file)`; mtime не участвует — стабильность для reuse);
- копирует payload в свою выходную папку; нечитаемый источник → элемент `status: failed`
  без payload (не роняет весь скан).

Три свойства: это builtin (обычный Python, без LLM), он детерминирован и является
единственным источником коллекций «из ничего» — дальше по I6 ни один агент коллекцию не
создаёт, только потребляет.

## 8. Map — управляемый параллелизм и агрегация

![Бригадир раздаёт одинаковые задачи трём рабочим и собирает результаты обратно](architecture/map-fanout.png)

Map — единственное место, где живёт fan-out. Агент обрабатывает один элемент; «прогнать на
всех» — обязанность движка (SPEC §10.3):

```yaml
- id: extract
  type: agent
  agent: source_processor@1
  map: scan.sources
  params: { workers: 3, min_ok: 1, on_item_failure: skip }
```

Механика:

- на каждый ok-элемент входной коллекции создаётся отдельный шаг (`extract:rfp-pdf`, …),
  переиспользующий общий жизненный цикл (§10); агент внутри видит только свой элемент и не
  знает о существовании остальных (I1);
- параллелизм ограничен `min(workers, свободные слоты провайдера)` — семафор per-provider из
  `providers.yaml.max_concurrent`, чтобы не выйти за лимиты API конкретной модели;
- failed-элементы входа не исполняются, но копируются в выходную коллекцию со `status: failed`
  (учитываются в stats) — «дырка» видна, а не теряется;
- по завершении собирается `_collection.json` выходной коллекции; если `ok < min_ok` или
  (`on_item_failure: fail` и есть failed) — нода failed;
- источник для `map:` не может быть произведён map/map_over-нодой (`E_NESTED_MAP`, v0.1);
  один map/map_over на ноду.

## 9. Loop и Select — control flow через артефакты

Это два примитива, реализующих условное поведение. Оба принимают решения только по
типизированным управляющим артефактам (принцип 5).

Loop (SPEC §10.3). Последовательность `body:r1 → critic:r1 → body:r2 → …`. Ключевые детали:

- номер раунда не хранится отдельно — он выводится из леджера (сколько body-шагов уже done);
  это исключает рассинхрон «счётчик vs факт»;
- перед body раунда r≥2 движок материализует в его `input/`: `_previous/<port>.<ext>` (выход
  body предыдущего раунда) и `_verdict/verdict.json` (вердикт предыдущего раунда) — только
  относительные пути (I1); в промпт добавляется секция revision;
- критик обязан выдать `verdict@v1` (проверяется гейтом и валидатором — `E_LOOP_SHAPE`);
  `approved` → выход ноды = выход body последнего раунда; `revise` на `max_rounds` → `pass`
  (взять последнюю версию, warning-событие) или `fail`;
- сборка выхода ноды идемпотентна при resume (как у map): `_out/<outName>.<ext>` пересоздаётся
  из выхода последнего раунда.

Select (SPEC §10.3). Из нескольких кандидатов (коллекции) выбирается победитель:

- 0 ok-кандидатов → нода failed; 1 ok-кандидат → селектор не запускается вовсе, нода done,
  выход = этот элемент (оптимизация: не тратить LLM на тривиальный выбор);
- иначе шаг селектора выдаёт `selection@v1`; `winner` обязан совпасть с одним из ok-slug —
  если нет, это failed_validation селектора и идёт в гейт-ретраи; после их исчерпания —
  `fallback: first_ok` (первый ok по порядку, warning-событие) или нода failed;
- экспортируемые `winner` и `winner_model` кладутся в node-запись леджера и доступны для
  `@<select>.winner_model`-биндинга (§4).

## 10. Жизненный цикл шага — единственная реализация

![Жизненный цикл шага: материализация входов → промпт → рантайм → гейт; ok ведёт в готово, провал — в архив попытки и повтор с фидбэком](architecture/step-lifecycle.png)

Всё — обычная нода, элемент map, раунд loop, селектор — исполняется одним и тем же кодом
`execute_agent_step` ([refract/steps.py](../refract/steps.py), SPEC §10.2). Дублирования нет:
меты и map лишь готовят входы и собирают выходы вокруг этого ядра.

Порядок (упрощённо):

1. Создать каталог шага, материализовать входы в `input/<port>/` (I1). Входы иммутабельны на
   всё время гейт-ретраев.
2. Собрать промпт из системной части (`prompt.md`) + сгенерированных из контракта секций
   inputs/outputs (+ revision / gate_feedback, если есть) → записать `prompt.md`.
3. Запустить рантайм с таймаутом. Инфра-ошибка (`completed=False`) → backoff-ретрай (base 2s,
   ×2, jitter, max 60s) до `infra_retries`. Таймаут → outcome `timeout`.
4. HITL-проверка: валидный `question.json` в выходе → в фазах 0–2 это `failed_agent`
   («interactive not supported yet»); полноценный HITL — фаза 3.
5. Гейт: для каждого не-optional produces-порта — файл существует, JSON по схеме, все rules.
   Успех → done/ok. Провал при оставшихся попытках → записать `gate_report.json`,
   заархивировать текущую попытку в `attempts/<n>/`, повторить с добавкой gate_feedback.
   Провал после `gate_retries+1` попыток → `failed_validation`.

Два принципиальных момента:

- Счётчики независимы. `gate_retries` (агент выдал невалидный результат — виноват агент) и
  `infra_retries` (рантайм упал — виновата инфраструктура) считаются раздельно и никогда не
  смешиваются.
- Никогда не перезаписываем in-place. Перед повторным прогоном текущие `prompt.md`, `raw.txt`,
  `agent.events.jsonl`, `output/`, `gate_report.json` уезжают в `attempts/<n>/`, `output/`
  создаётся заново (I2 + I9). Это делает историю попыток полной и совместимой с resume.

Таксономия исхода шага (`outcome`): `ok | failed_validation | failed_agent | failed_infra |
timeout`. Она нужна и для леджера, и для проекции в CLI/UI.

Отладочный след (I9): для каждого agent-шага сохраняются `prompt.md`, `raw.txt`,
`agent.events.jsonl` (по каждой попытке — в `attempts/`). Builtin-шаги хранят только выходы и
запись в леджере.

## 11. Архитектура движка — слои

![Слои движка сверху вниз: CLI, валидатор графа, снапшот, планировщик, жизненный цикл шага, артефакты/промпт/рантайм, state.json + events.jsonl, модели + реестр](architecture/engine-layers.png)

Снизу вверх:

- models/ + registry.py — фундамент. Каждый формат файла (pipeline.yaml, agent.yaml,
  state.json, коллекция) — pydantic-модель; ad-hoc парсинга YAML нет («форматы ЕСТЬ модели»).
  Реестр знает типы и проверяет совместимость рёбер.
- graph.py — загрузка + валидация + топосорт. Собирает все ошибки списком, не падает на первой.
- snapshot.py — заморозка. Копирует pipeline и пакеты агентов в `snapshot/`, пишет
  `resolved.yaml` (все дефолты и эффективные модели проставлены). Исполнение и resume читают
  только снапшот — правка агента во время рана на бегущий ран не влияет.
- scheduler.py — оркестратор (§12).
- steps.py — жизненный цикл шага (§10), единственная реализация.
- artifacts.py / prompt.py / runtime/ — обслуга шага: материализация и гейты; сборка промпта
  из jinja-шаблонов и контракта; абстракция рантайма (mock для тестов, opencode для прода).
- state.py / events.py — память и журнал (§13).

## 12. Планировщик — готовность, конкурентность, никакого polling

Планировщик отвечает на один вопрос в цикле: какие ноды сейчас можно запустить.

- Правило готовности: нода готова, когда все ноды-источники её входов (включая
  binding-зависимости от select) в статусе done или reused. Готовые исполняются конкурентно.
- Разворачивание примитива в шаги: готовую ноду scheduler превращает в набор вызовов
  `execute_agent_step` — один шаг (agent), N шагов (map), раунды (loop), один селектор (select),
  либо прямой вызов `run()` (builtin, без рантайма).
- Как узнаёт о завершении: не через файл. Всё живёт в одном процессе на asyncio; scheduler
  `await`-ит корутину шага и просыпается ровно в момент её `return`. Ноль polling, ноль гонок.
  Истина для scheduler — объект-леджер в памяти; `state.json` — его зеркало на диск для
  проекции и восстановления.
- Конкурентность под контролем: параллелизм внутри map — `min(workers, свободные слоты
  провайдера)` через семафор per-provider. Это защищает от превышения rate-limit конкретной
  модели, даже если `workers` большой.

`state.json` читается с диска ровно один раз — при resume нового процесса (§13).

## 13. Состояние: два уровня, атомарность, восстановление

Леджер (`state.py`, SPEC §9) — сердце надёжности. Два уровня:

- steps — атомы исполнения (`pending → running → done | failed | waiting_human | cancelled`,
  плюс `reused`), с outcome-таксономией (§10);
- nodes — узлы графа (`pending → running → done | failed | skipped`, плюс `reused`). Нода
  становится done только после сборки её выходов (для map — после записи `_collection.json`).
  Это делает сборку идемпотентной при resume: если все шаги done, а нода нет — пересобрать.

Гарантии:

- Атомарность (I3): `state.json` пишет только движок, только `tmp + os.replace`, одной записью
  на изменение. Крэш посреди записи не может оставить полуфайл.
- Event sourcing: параллельно с `state.json` пишется append-only `events.jsonl` (единственный
  писатель — asyncio-задача с очередью, она же присваивает монотонный `seq`). Типы событий:
  `run_state_changed`, `step_state_changed`, `node_state_changed`, `heartbeat`, `tool_call`,
  `log`. CLI и будущий WS/UI (фаза 2) — проекции этого журнала (`?from_seq=` → replay + live).
- Крэш-восстановление: при загрузке леджера все `running → pending` (и шаги, и ноды). Это и
  есть механизм resume — не «оптимизировать» его прочь. Дальше scheduler просто снова
  спрашивает «кто готов», пропуская done-шаги.

Режимы возобновления (SPEC §10.5):

- resume `<run>` — продолжить прерванный ран; `--retry-failed` (failed→pending),
  `--force-step <step_id>` (шаг → pending с архивацией; его нода и зависимые вниз пересобираются);
- rerun `--from NODE [--reuse RUN|last]` — новый ран, переисполняется множество
  `{NODE} ∪ descendants(NODE) ∪ {ноды с транзитивно изменившимся входом}`. Builtin-ноды
  всегда исполняются. Map-элементы диффятся по `(slug, source_hash)` против reuse-рана:
  изменённые/новые исполняются, прочие — `reused` (артефакты link_or_copy из старого рана).
  Это и есть окупаемость контентной адресации (§2, принцип 3).

Вся линковка идёт через единый хелпер `link_or_copy()` (symlink, при неудаче copy — важно для
Windows).

## 14. Рантайм и секреты

`AgentRuntime` — протокол с `run_step(spec) -> StepResult` и `close()` (SPEC §12). Движок
оценивает результат агента по файлам в `output/` (гейт), а не по `StepResult` — `StepResult`
лишь сообщает «инфра ок / упал / usage».

- MockRuntime — для тестов: словарь `{fnmatch(step_id) → сценарии}`, пишет заданные файлы в
  `output/`. Все тесты гоняются только на нём — без сети, ключей и реального opencode.
- OpencodeRuntime — прод: компилирует пакет агента в `.opencode/agent/<name>.md` (frontmatter
  с моделью и tools из маппинга `needs`) + `opencode.json` (провайдер + MCP). Обязан ограничить
  файловый доступ агента его workdir (I1) и убить процессы в `close()` даже на крэше.

Секреты (I8): рантайм получает env один раз на ран — объединение ключей провайдеров всех
моделей из `resolved.yaml` + MCP-токены из `needs` задействованных агентов. В папку проекта,
артефакты и промпты секреты не попадают никогда.

## 15. Валидация графа

Валидатор (`graph.py`, SPEC §8.3) собирает все ошибки списком `{code, node_id?, message}` —
не падает на первой. Порядок проверок: pydantic-схема → id/ссылки/существование агентов,
builtin'ов, типов → совместимость рёбер и map-правила → все не-optional входы подключены →
ацикличность (loop — атомарная вершина) → разрешимость моделей → ограничения v0.1 → security
warnings. Коды — закрытый enum (`E_YAML`, `E_TYPE_MISMATCH`, `E_CYCLE`, `E_LOOP_SHAPE`,
`E_NESTED_MAP`, `E_BINDING_ILLEGAL`, `E_AGENT_PRODUCES_COLLECTION`, `W_SECURITY`, …).

Показательный warning: `W_SECURITY` — нода, чей вход достижим от `builtin/scanner`, имеет
`bash`/`webfetch`/`mcp:*`. То есть данные из непроверенного `input/` текут в агента с опасными
capability — это флаг для ревью, но не блок.
