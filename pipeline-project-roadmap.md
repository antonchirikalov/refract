# Роадмеп проекта: движок пайплайнов с UI

Принцип нарезки: каждая фаза заканчивается работающим инкрементом, которым можно пользоваться. Движок строится раньше UI; UI раньше билдера; всё эффектное — после всего надёжного. Оценки — грубые, в неделях чистой работы одного человека с AI-ассистентом; календарно умножай на свой темп.

---

## Фаза 0 — Спека и ядро движка (3–4 недели)

Цель: пайплайн Extract из spectra бежит на новом движке через CLI.

- Спека форматов: `artifact_types.yaml`, пакет агента, `pipeline.yaml`, `project.yaml`, формат событий, REST/WS API (пишется сразу, реализуется по фазам).
- Реестр типов + валидатор графа (типы рёбер, обязательные входы, уникальные id).
- Исполнитель DAG: топосортировка, планировщик, map/collection, workdir-изоляция шага, материализация входов, стандартный хвост промпта из контракта.
- State-леджер (атомарный, перенос из spectra) + resume + status.
- Интерфейс `AgentRuntime` + адаптер opencode serve (переработка `opencode_client.py`), компиляция пакета агента в workdir.
- Миграция агентов Extract-пайплайна (scanner как builtin, source_processor, requirements_writer) в формат пакетов.
- CLI: `run / resume / status`.

Выход из фазы: результат нового движка на реальном входе не хуже spectra. Критик-цикл пока выключен (нет loop-ноды) — это осознанно.

## Фаза 1 — Control flow и надёжность (2–3 недели)

Цель: полный паритет всех трёх пайплайнов spectra + вещи, которых в spectra нет.

- Мета-нода `loop` (verdict@v1, revision-хвост, step id по раундам) и `select` (selection@v1, fallback, `map_over.models`, биндинг `@winner`).
- Валидационные гейты по схемам/правилам + автоматический ретрай с инжекцией ошибок гейта.
- Таксономия исходов (`failed_infra` ≠ `failed_agent` ≠ `failed_validation`), ретрай-политики, `on_item_failure`/`min_ok` для map.
- Троттлинг: семафоры per-provider, backoff на 429.
- `reuse_from + force` между ранами (rerun-from-node, инкрементальное добавление файлов).
- Снапшот рана (граф + параметры + хэши пакетов агентов).

Выход: три шаблонных пайплайна (Extract, Discovery, Solution Design) в виде `pipeline.yaml`, spectra можно замораживать.

## Фаза 2 — UI: локальный веб (3–4 недели)

Цель: коллега без терминала запускает пайплайн и смотрит результаты.

- FastAPI: REST (проекты, пайплайны, раны, параметры) + WebSocket (проекция `events.jsonl`).
- Экран проектов, folder-browser через бэкенд, создание пайплайна из шаблона.
- Канвас React Flow (read-only): статусы нод, map «7/9 ✓», loop «round 2/5» с раскрытием, security-бейджи.
- Панель ноды: модель (дропдаун по доступным ключам), workers, max_rounds, ретраи.
- Вьювер артефактов: markdown, JSON, картинки; промпт и лог шага.
- Run / resume / cancel / rerun-from-here из UI; история ранов.
- Лок графа на время рана.

Выход: первый релиз для других людей. Собери фидбэк здесь, до фаз 3–4.

## Фаза 3 — HITL и безопасность (1,5–2 недели)

- `question@v1`/`answer@v1`, состояние `waiting_human`, переживающее рестарт; вопросы агентов в чат-панель; `max_clarifications` и политики.
- Capability-тиры: network-согласие на проект, явное подтверждение dangerous-нод, security warnings валидатора («недоверенный вход + bash»).
- Инжекция секретов per-step (только нужный провайдер/MCP).

Выход: интерактивные пайплайны + систему можно давать людям, которым не доверяешь настройку.

## Фаза 4 — Чат-билдер (2–3 недели)

- Каталог агентов для билдер-LLM (карточки + типы + few-shot).
- Патч-операции (`add_node`, `connect`, …), цикл с валидатором до 3 попыток.
- Ревью в UI: карточка диффа в чате + подсветка изменений на канвасе, Apply/Discard.
- Ручное редактирование канваса: параметры, удаление нод, соединение рёбер с подсветкой совместимых портов.

Выход: «опиши пайплайн словами — получи граф». Главная демо-фича; делается последней, потому что опирается на всё предыдущее.

## Фаза 5 — Продуктизация (по потребности, не подряд)

Пул задач, приоритезировать по фактической боли:

- Electron-упаковка (React-фронт + Python sidecar), автообновление.
- Контентный кэш (opt-in per node), оценка стоимости рана до запуска.
- Библиотека агентов с версиями, пин версий в проекте; генерация нового агента из чата.
- Контейнерный санбокс для bash-нод.
- Дифф артефактов между ранами; экспорт пайплайна в standalone-скрипт.
- Собственный минимальный runner (litellm) как второй `AgentRuntime` — только если opencode начнёт мешать.
- Мультипроектность/несколько параллельных ранов.

## Сводка

| Фаза | Результат | Оценка |
|---|---|---|
| 0. Ядро движка | Extract бежит на новом движке (CLI) | 3–4 нед |
| 1. Control flow | Паритет со spectra + rerun/reuse | 2–3 нед |
| 2. UI | Локальный веб, релиз для коллег | 3–4 нед |
| 3. HITL + security | Интерактивность, тиры доступа | 1,5–2 нед |
| 4. Чат-билдер | Пайплайн из текста | 2–3 нед |
| 5. Продуктизация | Electron, кэш, библиотека агентов | по мере боли |

Итого до «продукта с чат-билдером» — порядка 12–16 недель чистой работы. Точки принятия решений: после фазы 2 (фидбэк пользователей может переставить фазы 3 и 4), после фазы 4 (нужен ли Electron или всем ок вкладка браузера).

Риски, за которыми следить: стабильность opencode serve API (митигируется интерфейсом AgentRuntime); качество патч-операций у билдер-LLM (митигируется шаблонами — продукт работает и без билдера); соблазн начать с UI вместо движка (не надо — UI без надёжного движка это демо, а не инструмент).
